Modern server software is configurable to a degree that few of its operators fully appreciate. A recent release of MySQL exposes over six hundred system variables, Apache httpd offers several hundred directives across its core and standard modules, and a Kubernetes cluster presents thousands of settable fields once custom resources are counted. Only a small fraction of these options bear on security, but that fraction is decisive. Misconfiguration is consistently among the leading causes of reported breaches, ahead of memory-safety defects in several industry datasets, and the specific failures are mundane: an authentication mode left permissive, a debug endpoint exposed, a cipher suite retained for backward compatibility, a log verbosity setting that suppresses the very records an investigation would need. What makes these failures durable is that nothing in the software distinguishes them from the hundreds of benign performance and behavior knobs sitting beside them in the same configuration file.

The current answer to this problem is manual curation. Organizations such as the Center for Internet Security publish hardening benchmarks that enumerate security-relevant settings for widely deployed software, with recommended values and rationale. These documents are careful and useful, but they are also slow, expensive, and narrow. A benchmark exists for a few dozen popular products and lags each product's release cycle by months, which means that newly introduced options, exactly the ones administrators are least familiar with, are the ones least likely to be covered. Automated approaches have taken two forms. Static analysis traces configuration variables to the code paths they influence and flags those reaching security-sensitive APIs, which is precise where it applies but requires source access, per-language tooling, and substantial engineering per project. Keyword matching over documentation is trivially portable but crude, since terms like "secure" and "auth" both overgenerate, appearing in performance options that mention authentication caching, and undergenerate, missing settings whose security consequence is described without any security vocabulary at all.

Our approach is to treat the identification of security-relevant settings as a text classification problem over the documentation that software already ships. Every configurable option in a mature project is accompanied by prose describing what it does, and that prose, written for administrators rather than for security analysts, encodes the semantics needed to make the judgment. A setting described as controlling whether client certificates are verified is security-relevant regardless of whether the word security appears; a setting described as adjusting a connection pool size is not, even if the surrounding section discusses authentication. Determining this requires reading comprehension rather than lexical matching, which is what pretrained language models supply.

Building the classifier required first building a dataset, and this was the larger part of the work. We extracted option-documentation pairs from the reference manuals of twelve widely deployed systems spanning databases, web servers, application servers, and container runtimes, yielding roughly nine thousand options after deduplication and the removal of deprecated entries. Labels came from two sources. Positive labels were derived by aligning options against published CIS benchmarks and vendor hardening guides, matching on option name with manual resolution of aliases and version drift. Because these sources are incomplete, options absent from them cannot be treated as reliable negatives, so we had two security practitioners independently annotate a stratified sample of unmatched options, resolving disagreements by discussion; inter-annotator agreement reached a Cohen's kappa of 0.79, which we take as an estimate of the ceiling on achievable accuracy. The resulting distribution is heavily imbalanced, with security-relevant options comprising under fifteen percent of the corpus, and we address this with class-weighted loss rather than resampling, having found that oversampling the minority class degraded precision without improving recall.

The model itself is deliberately unexciting: a transformer encoder pretrained on general text and further pretrained on a corpus of software documentation and security advisories, then fine-tuned for binary classification over the concatenation of option name, type, default value, and documentation text. We compare against a keyword baseline drawn from the security vocabulary used in prior work, a TF-IDF logistic regression, a gradient-boosted model over handcrafted features, and a general-domain encoder without the documentation pretraining stage. Evaluation uses two protocols. Within-project evaluation splits options randomly and measures standard classification metrics. Cross-project evaluation, which we consider the meaningful one, holds out entire systems from training, since the deployment scenario is applying the classifier to software for which no benchmark exists.

Under cross-project evaluation the fine-tuned model attains an F1 of 0.84 with precision 0.81 and recall 0.87, against 0.52 for the keyword baseline and 0.68 for TF-IDF logistic regression. Domain-adaptive pretraining contributes about four points of F1, concentrated in projects whose documentation style diverges from the training set. Recall is the metric we optimized for, on the argument that a missed security-relevant option is a silent risk while a false positive costs an administrator a few seconds of review, and the operating point can be shifted along the precision-recall curve to suit a given review budget. Error analysis shows that residual false negatives cluster in options whose security relevance is contextual, depending on deployment topology rather than on the option's own semantics, which is a limit inherent to reasoning from documentation alone.

We then applied the classifier to four systems for which no hardening benchmark exists and asked three independent security engineers to review its top-ranked predictions. They confirmed a large majority as genuinely security-relevant, including several options none of them had previously considered in that light, and two that led to concrete configuration changes in their own environments. This is the result we regard as the practical payoff: the method extends hardening coverage to the long tail of software that manual curation will never reach, and it does so at a cost of minutes per project rather than weeks. It does not replace expert judgment, and we do not propose it as an oracle for correct values, only for which settings deserve attention. Determining the right value for a flagged setting still requires knowing the deployment, and integrating our classifier with the configuration-value validation literature is the natural continuation of this work.
